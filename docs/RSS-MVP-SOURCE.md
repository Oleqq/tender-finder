# Tender Finder: источник ЕИС через RSS для MVP

## Статус реализации на 2026-08-25

В репозитории уже есть `TenderSource`, `EisRssSource`, URL allowlist, XML
parser, fixture importer, source runs, дедупликация по каноническому URL/
`regNumber`, first-poll silence, очередь matching и лимиты. Автоматический live
polling намеренно выключен переменной `RSS_LIVE_POLLING_ENABLED=false`: это
защита, а не недоделка. Он не будет включён, пока `SRC-00` не зафиксирует
проверенные EIS URLs, допустимые redirect-переходы, реальные поля и условия
источника. Тестовые XML-файлы — synthetic examples, не реальные тендеры.

## Решение

До получения доступа к сервисам отдачи информации ЕИС (СОИ) MVP получает новые закупки из публичных RSS-лент расширенного поиска `zakupki.gov.ru`.

Это рабочий временный источник для закрытого бета-запуска, а не окончательная замена СОИ. Он позволяет запустить поиск, уведомления и платную подписку без API-ключа, но не даёт гарантии полного охвата всей России при сотнях уникальных поисков.

Пример адреса ленты:

```text
https://zakupki.gov.ru/epz/order/extendedsearch/rss.html?...
```

Точную ссылку формирует сам портал после настройки расширенного поиска и нажатия кнопки RSS. На этапе разработки мы сохраняем несколько проверенных URL как тестовые сценарии, а параметры, которые можно безопасно генерировать из формы Mini App, фиксируем только после ручной проверки на портале.

## Почему используем этот подход

В качестве технического референса изучен проект [free-zakupki-gov-ru-monitor](https://github.com/stufently/free-zakupki-gov-ru-monitor), версия `0.2.2`, commit `162a977`. Он проверяет реальные RSS ЕИС и лицензирован под [MIT License](https://github.com/stufently/free-zakupki-gov-ru-monitor/blob/main/LICENSE).

Мы берём идеи и поведение, но пишем собственную реализацию на PHP/Laravel. Код Chrome-расширения, его UI, Service Worker и локальное browser storage в приложение не переносятся. Если когда-либо будет скопирована существенная часть исходного кода или тестовых данных, в репозитории Tender Finder нужно сохранить уведомление об авторских правах и текст MIT-лицензии.

## Что переносим в серверную реализацию

| Паттерн из референса | Реализация в Tender Finder |
|---|---|
| Опрос лент по расписанию | Laravel Scheduler запускает диспетчер каждую минуту; он ставит в Redis только ленты, которым пора обновиться |
| Дедупликация по `guid`, а при его отсутствии по ссылке | В RSS ЕИС обычно нет `guid`, поэтому ключ - нормализованный URL карточки и извлечённый `regNumber` |
| Первый успешный опрос без шквала уведомлений | Лента получает статус `initialized`; старые записи сохраняются для показа в Mini App, но уведомления отправляются только для более новых |
| Последний успех, попытка и ошибка по каждой ленте | Храним в БД; показываем в админке и отправляем алерт при повторяющихся сбоях |
| Таймаут, лимит размера ответа, разбор XML с понятными ошибками | HTTP timeout 30 секунд, размер до 5 МБ, безопасный XML-парсер; HTML вместо RSS, пустой и невалидный XML - отдельные ошибки |
| Последовательный polling с паузой | Глобальный Redis rate limit: не более одного запроса к ЕИС примерно раз в 1,5-2 секунды, плюс jitter |
| Проверка URL до и после redirect | Допускаем только HTTPS, `zakupki.gov.ru` и его поддомены, порт 443, разрешённые RSS-пути; никаких cookie и пользовательских URL произвольных хостов |
| Краткая сводка при большом числе результатов | Используем правило ТЗ: максимум 20 карточек в час на пользователя, затем сводка с топ-10 |

## Что RSS даёт, а что нет

RSS-элемент обычно содержит ссылку на карточку, название, дату публикации и часть описания: закон, заказчика, НМЦК и статус. Этого достаточно, чтобы найти новую закупку и показать первичную карточку.

RSS не является стабильным полным API. В нём могут отсутствовать регион, дедлайн, полный предмет закупки, ОКПД2 и вложения. Поэтому обработка двухступенчатая:

1. `EisRssPollJob` получает новую запись и извлекает `regNumber` и ссылку.
2. `EisNoticeFetchJob` один раз загружает публичную карточку и дополняет запись доступными полями.
3. `TenderNormalizer` приводит значения к нашему формату.
4. `MatchTenderJob` сравнивает нормализованный тендер с запросами пользователей.

Карточку ЕИС загружаем только для новой или изменившейся записи, а не при каждом показе пользователю. Если страница временно недоступна, тендер остаётся в очереди на повторную попытку; уже полученные RSS-данные не теряются.

## Модель данных

| Таблица | Назначение |
|---|---|
| `source_feeds` | Канонический RSS URL, хеш URL, фильтры, статус, расписание, последняя попытка, последний успех, ошибка |
| `source_feed_items` | Сырые записи ленты: ссылка, `reg_number`, дата публикации, хеш содержимого, время обнаружения |
| `tenders` | Нормализованные тендеры; уникальный ключ `(source, external_id)` |
| `search_queries` | Фильтры пользователя и связь с одним или несколькими `source_feeds` |
| `tender_query_matches` | Причина совпадения и оценка релевантности |
| `notification_deliveries` | Защита от повторных уведомлений |

Одна и та же каноническая лента хранится один раз и может использоваться несколькими запросами. При изменении фильтров создаётся новая запись `source_feeds`; старая лента отключается после того, как на неё больше никто не подписан.

## Ограничения MVP и безопасный масштаб

Не создаём отдельный бесконтрольный RSS polling на каждого пользователя. В закрытой бете:

- максимум 3 активных запроса на пользователя согласно тарифу Trial/Базовый;
- максимум 100 уникальных активных RSS-лент на весь сервис;
- интервал проверки ленты - 10 минут по умолчанию, с равномерным распределением по времени;
- пользовательские фильтры сначала поддерживаются для ключевых слов, НМЦК и закона; регион добавляется после подтверждения соответствующего параметра URL;
- при достижении лимита новых уникальных лент админка не создаёт их автоматически, а показывает оператору причину и предлагает дождаться освобождения лимита.

При одном запросе раз в 1,5-2 секунды полный обход 100 лент занимает около 3 минут. Это оставляет запас для 10-минутного интервала и не создаёт параллельную нагрузку на ЕИС.

RSS-подход подходит для закрытой беты с десятками пользователей и узкими поисковыми запросами. Он не должен использоваться как единственный национальный источник для цели 300+ пользователей и 1 000 одновременных клиентов. До массового запуска требуется подключение СОИ ЕИС или лицензированный поставщик данных с согласованными условиями и измеренной задержкой.

## Уведомления и онбординг

При первом создании запроса пользователю не рассылаются десятки старых закупок. Вместо этого Mini App показывает до пяти последних найденных результатов как «первичные результаты поиска». После нажатия «Включить мониторинг» фиксируется `monitoring_started_at`; только записи, обнаруженные после этой даты, отправляются в Telegram.

Так мы одновременно выполняем сценарий ТЗ «показать пример найденного тендера» и избегаем спама.

## Безопасность и эксплуатация

- Не отключаем проверку TLS. На VPS/Docker устанавливаем доверенный корневой сертификат НУЦ Минцифры по официальной инструкции, если он требуется для `zakupki.gov.ru`.
- Не используем прокси-ротацию, обход CAPTCHA или обход блокировок.
- Не передаём RSS URL, cookies и данные фильтров третьим лицам.
- Ограничиваем размер ответа, число повторов и время обработки; повторяем временные ошибки с экспоненциальной задержкой.
- В админке видны: число активных лент, время последнего успеха, задержка самой старой ленты, HTTP/XML/TLS-ошибки и число новых тендеров.
- Алерт отправляется, если лента не обновлялась дольше 30 минут или доля ошибок превысила 5%.

## План перехода на официальный источник

Контракт `TenderSource` остаётся единым:

```text
EisRssSource (MVP) → TenderNormalizer → tenders → matching → notifications
EisSoiSource (после доступа) ─┘
```

`EisSoiSource` должен возвращать те же нормализованные поля и использовать тот же внешний ID ЕИС. Тогда переход не меняет Mini App, админку, подписки, поисковые запросы и Telegram-бота; он меняет только канал получения данных.

## Критерии приёмки RSS-источника

1. Проверенная RSS-лента успешно обрабатывается по расписанию.
2. Запись с одним `regNumber` не создаёт дубль при повторном опросе или перезапуске worker.
3. Первый опрос не отправляет старые записи как новые уведомления.
4. HTML-страница, неверный XML, HTTP-ошибка, timeout и TLS-сбой видны в админке как разные причины.
5. Новая запись из тестовой RSS-ленты появляется в нашей БД и проходит матчинг не позднее 10 минут после появления в ленте.
6. При временной недоступности источника очередь не теряет данные и автоматически возобновляет опрос.
