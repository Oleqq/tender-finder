# Roadmap: B2C, тарифы, Telegram Stars и super-admin

## Продуктовая граница

Этот документ превращает текущие идеи в последовательный backlog. Он не
авторизует преждевременную реализацию платежей, LLM или массовых рассылок:
каждый блок начинается после зависимостей и проверок предыдущего.

## Клиентский опыт до и после покупки

```text
Preview → value tour → legal consents → 72h trial → active Basic → expired/paywall
                                                    └→ future PRO upgrade
```

- **Preview:** интерактивные макеты поиска, мониторинга, карточек и анализа;
  один источник demo-данных, явная маркировка «Пример», zero false urgency.
- **Trial:** один раз на серверно подтверждённый Telegram ID; продуктовые
  лимиты Базового плана и напоминания о завершении.
- **Paywall:** показывает разблокируемые действия и реальные лимиты, сравнение
  планов, цену в Stars, состояние invoice и восстановление после ошибки.
- **Basic:** объяснимый поиск и мониторинг. Оплата не скрывает данные клиента
  и не удаляет его запросы после завершения доступа — они замораживаются.
- **Future PRO:** запускается только после quality gate для scoring и анализа
  ТЗ, с прозрачным объяснением факторов и обратной связью пользователя.

## Разделение задач

| Поток | Ближайший результат | Следующий результат | Внешний блокер |
|---|---|---|---|
| Frontend foundation | Меньше blur/градиентов, библиотека компонентов, motion rules | Preview, paywall и access gates на demo-данных | Нет |
| Frontend admin | Ролевой entry point и admin-shell на demo-данных | Дашборд, Users, Campaigns, Ops, Audit | Нужны реальные API для данных |
| Telegram backend | Код проверки `initData`, session, `/start`, `/help`, consents и trial готов | VPS activation, reminders и real bot smoke-test | PostgreSQL, Redis, legal URLs, Telegram secrets |
| Tender core | Query API, fixture RSS adapter, дедупликация и deterministic matching готовы | SRC-00, live polling и delivery smoke-test | Набор RSS/канал ЕИС, VPS |
| Commerce | Plan/entitlement domain и paywall API | Stars invoice, pre-checkout, successful payment, refund | Цены/условия, PostgreSQL/Redis |
| Admin backend | Policy, audit events, read models | Campaign queue, limits, system-health aggregation | Ранее перечисленные домены |
| PRO intelligence | Схема feedback и evaluation dataset | Scoring + ToR analysis после quality/cost gate | Измерения и решение о модели |

## Commerce: граница MVP

Только сервер является источником правды о цене, invoice, оплате, доступе и
возврате. В таблицах потребуются минимум `plans`, `subscriptions`, `payments`,
`entitlements` и `billing_events`; уникальные idempotency keys и Telegram
payment charge ID не позволят повторной доставке события повторно выдать
доступ. Продление, лимиты и возвраты проектируются как отдельные переходы
статусов, а не как условие внутри React-компонента.

Telegram Stars — обязательный первый способ оплаты цифрового доступа внутри
Mini App. Внешний web-checkout в scope не входит: его можно рассматривать
отдельно после юридического и коммерческого решения.

## Super-admin policy

- В конфигурации развёртывания хранится ровно один bootstrap Telegram ID;
  идентификатор не попадает в commit, клиент и публичные docs.
- После успешной server-side валидации `initData` Laravel создаёт/находит
  пользователя и присваивает `super_admin` при совпадении ID.
- У всех остальных — `subscriber`; plan, trial и entitlement не меняют роль.
- Policy проверяется на сервере везде, включая отчёты, экспорт, кампании,
  исходники и отправку сообщений. Скрытая кнопка не является защитой.
- Действия super-admin логируются: actor, действие, объект, безопасная сводка,
  время, request/correlation ID. Значения секретов и лишние ПДн не пишутся.

## Кампании и сообщения от бота

| Тип | Пример | Правило |
|---|---|---|
| Операционный | завершение trial, сбой важного мониторинга | Системный шаблон, идемпотентность, частотный лимит |
| Продуктовый | доступна новая функция | Уместный сегмент, уважение пользовательских настроек |
| Маркетинговый | срок скидки, предложение плана | Отдельное согласие/настройка, preview, quiet hours, отписка |
| Персональный | ответ на обращение | Только выбранный пользователь, явный контекст и аудит |

Перед массовой отправкой admin видит размер аудитории и тестовый рендер;
очередь соблюдает Telegram rate limits, а отчёт показывает queued/sent/failed.
Нельзя обещать доставку пользователю, который не инициировал чат с ботом.

## Персональный scoring: после базового продукта

Базовый matching сначала остаётся детерминированным и объяснимым: ключевые и
минус-слова, регион, бюджет, дедлайн и явно показанные причины. Для будущего
PRO scoring не нужен необъяснимый «магический балл»: профиль составляется из
фильтров и добровольной обратной связи «подходит / не подходит»; результат
показывает факторы и уверенность. Только после offline-evaluation, контроля
стоимости, качества и обработки данных добавляется LLM-анализ ТЗ.

## Definition of ready для нового блока

1. Есть пользовательский сценарий, модель данных и server-side policy.
2. Есть loading, empty, error, offline и retry состояния.
3. Есть unit/integration tests для денег, прав и идемпотентности либо feature
   tests для UI без API.
4. Метрики не имитируются: у каждой есть источник, окно времени и определение.
5. В `PROGRESS.md` внесён результат, проверки и внешние блокеры.
