# UX-аудит Mini App

Дата: 21 сентября 2026 года. Область: пользовательский путь в Telegram Mini App, а не внутренняя операторская консоль.

## Цель интерфейса

Пользователь приходит не управлять источниками и очередями, а быстро ответить на три вопроса: есть ли подходящая закупка, что сделать сейчас и работает ли мой мониторинг. Всё остальное должно появляться только по действию пользователя или при состоянии, которое требует внимания.

## Принципы

1. На каждом экране один основной следующий шаг.
2. Сначала результат и дедлайн, затем фильтры, диагностика и настройки.
3. Не использовать технические термины, внутренние коды, Telegram ID или детали транспорта.
4. Ошибка доставки не равна ошибке мониторинга: пользователь видит понятное последствие и автоматическое продолжение работы.
5. Редкие и необратимые действия находятся в «Управлении», а не конкурируют с основным действием.
6. Инструменты владельца не являются частью основной навигации подписчика.

## Карта основного потока

```text
Обзор
  ├─ есть действие → открыть карточку закупки → участие и задачи
  └─ нет действия → настроить мониторинг → лента совпадений

Лента
  ├─ быстрый поиск / личный статус
  └─ фильтры, источник, сохранённые виды → раскрыть при необходимости

Мониторинг
  ├─ «Проверить сейчас»
  ├─ состояние требует внимания → диагностика раскрыта
  └─ штатное состояние → диагностика свёрнута, доступна по запросу
```

## Внесённые изменения

- Основная нижняя навигация едина для подписчика и владельца: «Обзор», «Тендеры», «Профиль». Операторские маршруты остались защищёнными серверным middleware и доступны владельцу из свёрнутого блока профиля.
- Обзор больше не повторяет один и тот же сценарий в нескольких карточках. Метрики «просрочено» и «на сегодня» не показываются как нули; основной CTA зависит от доступа.
- В ленте сразу видны поиск и личный статус. Источник, дополнительные фильтры, сброс и сохранённые представления перенесены в раскрываемый блок. Если фильтр уже активен, блок открыт и помечен.
- Карточка мониторинга показывает одну главную операцию и короткое состояние. Вся телеметрия запуска раскрыта только по запросу, но остаётся раскрытой при ошибке, очереди, паузе или первом запуске. Внутри сохраняется различие «ответ получен, совпадений нет» и «источник недоступен».
- Редкие операции мониторинга (история, пауза, изменение, копирование, заморозка, удаление) перенесены в «Управление».
- В карточке закупки первыми остаются статус, причина совпадения, сумма и срок. Текст закупки, мониторинг и объяснимая оценка правил раскрываются по запросу.
- В истории уведомлений статус `failed` теперь формулируется как «Не доставлено»; рядом даётся нетехническое пояснение, что мониторинг продолжает работать.

## Проверочная матрица

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Нет срочных задач | Не показывать пустые числовые карточки; предложить следующий полезный шаг. |
| Есть просроченная задача | Показать её в начале обзора с датой и переходом в работу. |
| Обычный мониторинг без новых совпадений | Короткое штатное состояние без развёрнутой телеметрии. |
| Источник не ответил | Автоматически раскрыть понятную причину, последний успех/ошибку и следующую попытку. |
| Ошибка Telegram | Не раскрывать транспортную диагностику и не создавать впечатление, что мониторинг остановлен. |
| Владелец приложения | Получает операторские инструменты после осознанного раскрытия; пользовательский поток не меняется. |
| Пользователь без прав | Не может видеть чужие тендеры, доставки, команды или административные маршруты; это обеспечено серверными тестами и middleware. |

## Ограничения валидации

Проверка реального Telegram Desktop зависит от того, что окно доступно средству автоматизации. Если окно недоступно, проверяются серверные feature-тесты, TypeScript-сборка и локальная вёрстка в изолированном окружении. Для выдачи административной роли username недостаточен: роль привязана только к верифицированному Telegram ID на сервере.
