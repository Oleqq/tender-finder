# Загрузка Mini App на телефонах · 19 октября 2026

Коллега сообщил в 14:58 МСК, что у двух получивших доступ сотрудников Mini
App остаётся на заставке Telegram. На присланном кадре виден нативный экран
загрузки, без интерфейса сайта и сообщения об ошибке.

## Проверено

- В production на момент проверки шесть контейнеров работают; `web`, БД и
  Redis были здоровы. Пробный запрос `/health` с компьютера ответил `200`.
- Между 14:58 и 15:00 МСК в логах `web` есть только плановые `/health` и
  Telegram webhook. Запроса страницы Mini App или `/telegram/session` нет.
  Это указывает на проблему до авторизации пользователя; изменение роли в
  Laravel не может остановить нативную заставку до первого HTTP-запроса.
- В БД один из ранее настроенных владельческих Telegram ID не появился.
  Другой владелец смог пройти `/telegram/session` позднее, в 16:07 МСК:
  сервер отдал страницу, JS/CSS, Telegram SDK и ленту тендеров, после чего
  принял запрос быстрого поиска.
  Скриншот не позволяет однозначно связать эти ID с именами Вари и Ромы.
- Позднее этот же владелец написал в рабочем Telegram-чате, что приложение
  загрузилось после отключения VPN. Для одного из двух телефонов влияние
  сетевого маршрута подтверждено повторной попыткой.
- `ufw` на VPS выключен, базовое правило IPv4 INPUT — `ACCEPT`. Это не
  исключает ограничения на стороне сети или провайдера хостинга.
- Технический адрес `200.165.238.247.sslip.io` отдаёт A-запись, но не
  AAAA-запись. С рабочего Mac два из трёх прямых IPv4 HTTPS-запросов к нему
  завершились тайм-аутом TCP; третий ответил `200`. Три соединения через
  IPv4-mapped IPv6 socket ответили `200`. SSH по IPv4 к тому же VPS тоже
  периодически не устанавливает соединение до баннера.
- На рабочем Mac в момент диагностики VPN был подключён. При нём Mini App
  всё же открыл экран тендеров в Telegram Desktop. Значит, сбой соединения
  непостоянный и зависит от конкретного маршрута; успешный запуск на Mac не
  опровергает жалобу с телефонов.

**Вывод:** для одного участника зависание связано с VPN/маршрутом до
технического адреса, а не с серверной ролью. Для второго рабочая гипотеза
та же, но точное устройство, оператор, версия Telegram и результат открытия
`/health` на телефоне пока не получены. Причину второго зависания пока нельзя
считать подтверждённой.

## Повторная проверка 19 октября

- С рабочего окружения прямой HTTPS-запрос к
  `https://200.165.238.247.sslip.io/health` ответил `200`, а имя разрешилось
  в `200.165.238.247`. Это подтверждает, что сервер и TLS доступны по одному
  текущему маршруту, но не объясняет путь через VPN конкретного пользователя.
- `sslip.io` — технический DNS-сервис: имя содержит IP и возвращает этот IP.
  Текущий адрес имеет только IPv4. Внутренний IPv6-маршрут контейнеров **к**
  Telegram не даёт пользователям IPv6-маршрут **к** Mini App.
- Официальный Telegram Web App SDK уже отдаётся с того же origin, что и
  приложение (`/vendor/telegram-web-app-63.js`); отдельная блокировка
  `telegram.org/js/telegram-web-app.js` не объясняет этот случай.
- По имеющимся данным нельзя отличить фильтрацию `sslip.io` в DNS VPN от
  тайм-аута/фильтрации соединения VPN → IPv4 VPS. Для различения нужен
  результат `/health` и DNS-ответ именно на проблемном VPN, плюс время
  повторной попытки для сверки серверных запросов.

Постоянный путь устранения: домен под управлением владельца и входной HTTPS
с устойчивой доступностью из разных сетей; если VPS остаётся только IPv4,
двухстековый CDN/прокси либо перенос на подходящий хостинг. Простое новое
имя с той же проблемной IPv4-точкой не гарантирует исправления.

## Скриншот `/health` от пользователя

На присланном снимке Telegram-браузер показывает JSON
`{"status":"ok","application":"Tender Finder"}` для технического домена.
Это доказывает доступность короткого HTTPS-запроса с данного устройства в
момент снимка. Снимок не показывает состояние VPN и не проверяет путь `/open`,
JavaScript/CSS или отдельный режим Mini App WebView. Гипотеза полной DNS-
блокировки домена для этого устройства ослаблена, если VPN на снимке включён.
Пользователь сообщил, что сразу после проверки `/health` Mini App открылось,
причём VPN оставался включённым. Следовательно, этот VPN не блокирует запуск
постоянно; предыдущая неудачная попытка была временной. Нельзя установить,
помогла ли сама проверка `/health` или приложение открылось бы и без неё.
Состояние VPN именно в момент снимка `/health` отдельно не подтверждено.

В независимой проверке с рабочего компьютера `/open` и главные JS/CSS-файлы
ответили `200`; это контроль работоспособности сервера по другому маршруту,
а не проверка телефона пользователя. Следующий точный тест на **том же
телефоне при том же VPN**: открыть `/open` в обычном браузере Telegram и
сразу после этого нажать кнопку Mini App; записать время обеих попыток.
Если `/open` загрузит интерфейс и файлы, но кнопка останется на нативной
заставке, исследовать Telegram `requestWebView`/WebView и настройки VPN.

## Подготовленная диагностика 20 октября (локально, ещё не на VPS)

Новые Laravel-события `http.request.completed` пишут `request_id`, метод,
шаблон маршрута, статус, длительность, ID вошедшего пользователя и платформу
`ios`/`android`/`other`. Ошибки запроса получают `http.request.failed` с
классом исключения и тем же `request_id`; отклонённый `initData` тоже содержит
этот ID. Заголовок `X-Request-ID` в ответе помогает связать ошибку с записью
Laravel. URL с query string, тело запроса и Telegram `initData` в эти события
не попадают. В Caddy подготовлен JSON access log со статусом, временем,
маскированным IP и путём только для `/`, `/open`, `/health`,
`/telegram/session` и файлов Mini App. `request_id` связывает записи Caddy и
Laravel для ответа приложения; детали хранения — в
[VPS-DEPLOYMENT](VPS-DEPLOYMENT.md). Эти изменения ещё не развернуты, поэтому
искать такие события в старых логах VPS бесполезно.

После релиза для новой попытки записать время по Москве, сеть и состояние VPN.
На VPS из `/opt/tenderfinder` посмотреть соответствующий интервал:

```bash
docker compose -f compose.production.yml logs --since=30m web
docker compose -f compose.production.yml exec caddy tail -n 200 /var/log/caddy/access.log
```

Если в Caddy нет `/open` в нужное время, запрос не дошёл до HTTP-сервера;
проверить DNS, маршрут, TLS и открытие кнопки Telegram на телефоне. Если
`/open` есть, сопоставить его `request_id` с Laravel, статусом
`/telegram/session` и загрузкой `/build/*` и SDK. Ответ `200` для `/health`
показывает доступность одного короткого запроса, но сам по себе не доказывает
успешную загрузку Mini App.

## Следующая проверка и устранение

1. На каждом телефоне открыть `/health` того же адреса в Safari отдельно
   через LTE и Wi-Fi, записать результат и время. Если Safari не показывает
   `ok`, Mini App до приложения не доходит.
2. По полученному времени сопоставить входящие HTTP-запросы и
   `/telegram/session` с сервером. Если HTTP есть, но UI не появляется,
   снять ошибку WebView/JS и проверить загрузку asset-файлов.
3. Для постоянного исправления заменить технический `sslip.io` на домен с
   управляемым HTTPS и доступным с разных сетей маршрутом, при необходимости
   через двухстековый прокси/CDN. Одна смена имени с сохранением того же
   недоступного IPv4-маршрута проблему не решит. Обновлять одновременно
   `APP_DOMAIN`, `APP_URL`, `TELEGRAM_MINI_APP_URL` и URL Mini App у бота;
   сначала проверить TLS, редиректы, вход и платежи на новом origin.

См. также [TELEGRAM-NOTIFICATION-FLOW](TELEGRAM-NOTIFICATION-FLOW.md):
исправление кнопок и пустого командного дайджеста — отдельная задача.
