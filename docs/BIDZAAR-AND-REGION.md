# Bidzaar и ЭТП РЕГИОН

Обновлено 16 октября 2026 года. Оба источника включены на production.
ЭТП РЕГИОН и Bidzaar успешно опрашиваются.

## Bidzaar

Поддержка указала [Swagger API для агрегаторов](https://bidzaar.com/api/aggregator_integrator/swagger/index.html),
но 16 октября этот адрес ответил HTTP 404. Сам API закупок с выданным
`integratorId` ответил HTTP 200.
Метод `GET /api/aggregator_integrator/{integratorId}/procedures/purchases`
возвращает закупки и их изменения. Это API для тендерных агрегаторов, а не
[API для поставщиков](https://bidzaar.com/blog/api-dlya-postavshchikov) с
токеном из профиля отдельной компании. Для нашего адаптера нужен выданный
Bidzaar `integratorId` в формате UUID.

### Подключение к TenderFinder

1. Поддержка Bidzaar выдала `integratorId` для метода `procedures/purchases`.
   Не добавлять его в Git, документацию и логи. Если нужен договор или
   подтверждение условий использования данных в коммерческом TenderFinder,
   запросить это отдельно: в ответе поддержки условий не было.
2. Публичное описание API ограничивает размер порции 1000 процедур и глубину
   `FromDate` 14 днями. Оно говорит, что интервал повторных запросов выбирает
   агрегатор; числовой лимит запросов в минуту или сутки и стоимость доступа
   не указаны. Поддержка также не сообщила их — при необходимости запросить
   письменное подтверждение. Ответы проверенных запросов не содержали
   `RateLimit` или `Retry-After`.
3. Учесть ограничения выдачи: не более 1000 процедур за запрос; следующая
   порция получается курсором `FromDate` по `lastModified`. Запрос с датой
   старше 14 дней возвращает ошибку. После простоя дольше 14 дней полную
   историю через этот метод не восстановить. Адаптер начинает с последних
   13 дней, опрашивает по умолчанию каждые 15 минут и ограничивает один опрос
   100 порциями по 500 процедур; частоту по умолчанию держать на 15 минутах.
   `PageNumber=1` при живой проверке вернул пустой массив, хотя записи были.
   Следующую порцию получать с `FromDate=lastModified` последней записи и
   `PageNumber=0`: граничная запись повторяется, поэтому импорт удаляет дубли.
4. Живой ответ локально проверен на 1000 процедурах: парсер принял все записи,
   включая ссылки вида `/process/light/...`. Первый production-опрос 16 октября
   обработал 7814 изменений и сохранил 2510 открытых закупок за 23 секунды.
   Первый снимок не создал уведомлений. Повторный опрос успешно обработал 21
   изменение, создал 12 новых записей и не продублировал ранее сохранённые.
5. Идентификатор хранится в защищённом
   `/opt/tenderfinder/.env.production` (режим `600`), вне Git и логов.
   URL источника в БД не содержит идентификатор. Production использует параметры
   ниже; контейнеры кэшируют конфигурацию при запуске.

   ```dotenv
   BIDZAAR_ENABLED=true
   BIDZAAR_INTEGRATOR_ID=<UUID, выданный Bidzaar>
   BIDZAAR_POLL_INTERVAL_SECONDS=900
   REDIS_QUEUE_RETRY_AFTER=360
   ```

6. Для ручной проверки запустить опрос командой
   `docker compose --env-file .env.production -f compose.production.yml exec -T scheduler php artisan tenders:dispatch-bidzaar`
   из `/opt/tenderfinder`. Проверить `source_feeds`, `source_runs`, количество
   импортированных `tenders` и ссылки на площадку. Проверка доставки
   уведомления по новой подходящей закупке ещё не проводилась: второй опрос
   не создал новых совпадений. Ошибки API, формата и курсора видны в
   `source_runs`; до устранения ошибок источник нельзя считать работающим.

В приложении добавлен источник `bidzaar`: опрос официального API с курсором,
проверка структуры и ссылок, импорт карточек, персональное сопоставление,
очередь и статус источника. Первый снимок сохраняет только открытые процедуры
и не рассылает старые. Последующие опросы обрабатывают изменения статуса.
Проблема получения порции или продвижения курсора фиксируется как ошибка:
неполная выдача не считается успешной. В коде источник по умолчанию выключен;
на текущем production он включён.

Дополнительный вопрос поддержке: «Спасибо за доступ. Подтвердите, пожалуйста,
есть ли лимит запросов на `integratorId` в минуту или сутки, платный тариф
или условия показа карточек закупок пользователям коммерческого агрегатора?»

## ЭТП РЕГИОН

[Публичный поиск](https://torgi.etp-region.ru/app/SearchLots/page?SearchLots.typeSearchLots=Sall)
открывается по HTTP 200. Его HTML содержит только контейнер `gwtSearchPanel`;
список процедур подгружается кодом GWT через внутренний `/searchServlet`.
Сетевой запрос браузера проверен на живой странице. Прямые GET запросы с
`types=["BUYING"]`, `state=["ALL"]`, сортировкой по дате размещения и
порциями по 100 вернули JSON 200. На первых двух порциях получены даты,
состояния, номера, цены и прямые ссылки на лоты; `min=100` вернул следующую
порцию. Это внутренний интерфейс сайта, опубликованной спецификации API нет.

Источник `etp_region` получает только недавние закупки: до 14 дней от даты
размещения, не более 10 страниц за опрос. В импорт идут лоты со статусом
«Идёт приём заявок». Цены очищаются от HTML; локальное время дедлайна
переводится из указанного на площадке смещения относительно МСК. При сбое
формата, нарушении сортировки или исчерпании лимита страниц опрос считается
неуспешным. Источник может пропустить закупки, размещённые более 14 дней
назад, даже если они ещё открыты.

На production включён источник со следующими параметрами; при новом
развёртывании сначала проверить доступ из сети сервера:

```dotenv
ETP_REGION_ENABLED=true
ETP_REGION_PAGES_PER_POLL=10
```

После настройки выполнить `php artisan tenders:dispatch-etp-region`, сверить
несколько карточек и дедлайнов с сайтом, затем проверить следующий опрос. Поскольку
`/searchServlet` служит интерфейсу сайта, площадка может поменять его формат
без объявления; ошибки сохраняются в `source_runs`.
