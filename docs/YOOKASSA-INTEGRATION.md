# ЮKassa: разовая продажа на отдельном сайте

## Состояние на 29 октября 2026 года

Первый технический сценарий — разовая покупка доступа на самостоятельном
внешнем сайте. Серверный `YooKassaClient` выпущен: он создаёт платёж с ключом
идемпотентности и читает статус по официальному API. Ключ магазина остаётся
на сервере; транспорт проверен тестами без настоящих платежей.

**Реальные продажи закрыты**, `YOOKASSA_ENABLED=false`.
Серверный каталог цен и `subscription_orders` уже работают в
[защищённом demo](DEMO-CHECKOUT.md), но не связаны с ЮKassa.
Нет работающей привязки внешнего покупателя к Telegram, provider webhook,
фискальных чеков, возвратов и выдачи доступа по настоящей оплате.
В Mini App нет ссылки на внешнюю кассу; исторические таблицы Stars не
используются API-клиентом ЮKassa.

## Текущая конфигурация

| Переменная | Назначение |
|---|---|
| `YOOKASSA_ENABLED` | Разрешение **новых** запросов создания платежа; по умолчанию `false`. |
| `YOOKASSA_SHOP_ID` | Идентификатор тестового или реального магазина. |
| `YOOKASSA_SECRET_KEY` | Секретный API-ключ магазина; только server environment. |
| `YOOKASSA_REQUEST_TIMEOUT_SECONDS` | Тайм-аут вызова API, по умолчанию 15 секунд. |

Чтение статуса уже созданного платежа доступно при выключенном
`YOOKASSA_ENABLED`, если сервер сохранил действующие учётные данные. Это
нужно для сверки платежей после остановки новых продаж. Само по себе
изменение флага не открывает настоящую оплату: пользовательский путь
ЮKassa не подключён.

## Следующие работы перед тестовым магазином

1. Цены и периоды уже заданы в `SubscriptionCatalog`. Зафиксировать продавца,
   получателя чека и договорные условия доступа, отмены/возврата. Определить фискальный сценарий и данные
   чека с бухгалтером и юристом. Не использовать прежние цены XTR.
2. Адаптировать существующие demo-заказы к реальному провайдеру с уникальными
   `order_id`, `provider_payment_id` и `Idempotence-Key`. Связь внешнего
   покупателя с Telegram-аккаунтом должна быть подтверждаемой, а не вводом
   чужого Telegram ID.
3. Сделать независимый внешний путь покупки с серверной ценой и
   `confirmation_url`. Не размещать кнопку ЮKassa или переход на checkout в
   Mini App до отдельного согласования с правилами Telegram.
4. Получать `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
   Проверять объект повторным GET через API, сверять магазин, заказ, сумму и
   валюту. Обрабатывать повторы и изменения состояния идемпотентно. Выдавать
   доступ только после подтверждённого `succeeded`.
5. Проверить на тестовом магазине оплату, отмену, повтор webhook, возврат,
   чек и истечение срока доступа. Только после этого рассматривать реальный
   магазин и выпуск.
